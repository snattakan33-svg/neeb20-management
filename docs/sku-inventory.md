# จัดการสินค้า / SKU / สต๊อก — Demo v0.7.0

## เปิดบน Windows

1. ดาวน์โหลด ZIP ของสาขา `neeb20/prototype-demo` จาก GitHub แล้วแตกไฟล์ออกก่อน
2. ติดตั้ง Node.js 24 LTS ครั้งแรกจาก https://nodejs.org
3. ดับเบิลคลิก **START-NEEB20.cmd** คงหน้าต่างคำสั่งไว้ เว็บไซต์เปิดที่ http://127.0.0.1:3000 หลังเซิร์ฟเวอร์พร้อม ไม่ต้อง npm install
4. เลือก **ผู้จัดการทดสอบ 01** → เมนู **สินค้า / SKU / สต๊อก**

หากมีเซิร์ฟเวอร์รุ่นเก่าทำงาน ให้กด Ctrl+C ในหน้าต่างนั้นก่อนเปิดรุ่นใหม่ อย่าลบฐาน `.data/demo.sqlite` เพื่อแก้ปัญหาพอร์ตถูกใช้ หากต้องการตัวอย่างกำไร/กระทบยอดแยกฐาน ยังใช้ `OPEN-PROFIT-DEMO.cmd` (3002) หรือ `OPEN-RECONCILIATION-DEMO.cmd` (3001) ได้ตามเดิม ไม่มีการเติมข้อมูลตัวอย่างเข้าฐานเดิมโดยอัตโนมัติ

**ทุกยอดและสินค้าเริ่มต้นเป็นข้อมูลทดสอบ** ระบบยังไม่เชื่อมธนาคาร อุปกรณ์ หรือข้อมูลขายจริง การเปิดไฟล์ `NEEB20-DEMO.html` เป็น Local Demo ใช้ทดลองหน้าจอเท่านั้น ข้อมูลไม่ใช่ฐานกลางถาวร

## เพิ่มและแก้ข้อมูลผ่านเว็บ

กด **เพิ่ม SKU ใหม่** เพื่อเปิดแบบฟอร์มสินค้าเดิม กรอก SKU ชื่อ หมวด หน่วยนับ ราคาทุน ราคาขาย สต๊อกขั้นต่ำ และยอดตั้งต้น หากมีสต๊อกตั้งต้นจะสร้างรายการเคลื่อนไหวและล็อตพร้อมผู้ทำ/เวลา ไม่แก้ยอดลอย ๆ

รูปภาพเลือกได้สองวิธี: ลิงก์ HTTPS หรืออัปโหลด PNG/JPEG/WebP ขนาดไม่เกิน **120 KB** รูปอัปโหลดเก็บใน SQLite พร้อมข้อมูลสินค้า ใช้หลายเครื่องผ่านเซิร์ฟเวอร์เดียวกันได้ ไม่ต้องอัปโหลดไปบริการอื่น รูปภายนอกต้องคงลิงก์ให้เปิดอ่านได้ ขนาดเล็กเหมาะกับต้นแบบ ไม่ใช่ระบบคลังรูปขนาดใหญ่

ตารางแสดง SKU ชื่อ รูป หมวด หน่วย ทุนมาตรฐาน ราคาขาย กำไรต่อชิ้น คงเหลือ ขั้นต่ำ และสถานะ เจ้าของร้านใช้บทบาทผู้จัดการจึงเห็นทุน/กำไร พนักงานเห็นเฉพาะข้อมูลขายและสต๊อก ค้นหาจาก SKU ชื่อ บาร์โค้ด หมวด และ SKU เดิมได้ ตัวกรองหมวด/สถานะใช้ร่วมกับรายการ POS ช่องค้นหา POS ด้านบนก็มีผลกับรายการที่แสดง ล้างช่องค้นหาทั้งสองเมื่อจะดูสินค้าทั้งหมด

สถานะเรียงความสำคัญ:

- **ปิดขาย:** ผู้จัดการปิดขาย ไม่แสดงเป็นตัวเลือกเพิ่มสินค้าในบิล Station และชำระสินค้าในบิลเก่าที่ปิดขายไม่ได้จนจัดการรายการ
- **สินค้าหมด:** เปิดขายแต่คงเหลือ 0
- **สต๊อกต่ำ:** คงเหลือมากกว่า 0 และไม่เกินขั้นต่ำ
- **พร้อมขาย:** คงเหลือเกินขั้นต่ำ

แก้ชื่อ รูป หมวด หน่วย ขั้นต่ำ ราคา หรือทุนด้วย **แก้ไข SKU** การแก้ข้อมูลนี้ไม่รับจำนวนสต๊อกที่ต่างจากเดิม ต้องใช้รับเข้า/ปรับ/ตรวจนับเสมอ เปิด/ปิดขายแยกปุ่มและต้องระบุเหตุผล

### เปลี่ยนรหัสที่เคยขายแล้ว

ใช้ ID สินค้าเดิมตลอด การเปลี่ยน SKU ต้องติ๊กยืนยันและกรอกเหตุผล เก็บก่อน/หลัง ผู้ทำ เวลา และเก็บรหัสเดิมเป็น alias ค้นหาได้และสงวนไม่ให้สินค้าอื่นใช้ซ้ำ รวมถึงการเปรียบเทียบตัวพิมพ์ใหญ่/เล็กและ Unicode แบบเต็มความกว้าง

รายการขายใหม่เก็บ SKU ชื่อ หน่วย ราคาขาย และต้นทุนเป็น snapshot รายการเก่าไม่ถูกเขียนใหม่เมื่อเปลี่ยนรหัส รายงานรวมยอดด้วย ID สินค้า จึงไม่แยกสินค้าชิ้นเดียวกันเป็นสองรายการหลังเปลี่ยนรหัส หากรายการเก่ามีเพียง ID จะยังอ้างอิง ID เดิมโดยไม่สร้างรหัสในอดีตขึ้นเอง

**ไม่เปิดให้ลบสินค้าแบบถาวร** แม้ยังไม่ขาย เพื่อรักษาบิลเปิด สต๊อก และประวัติราคา ใช้ปิดขายแทน

## รับเข้า / ปรับเพิ่มลด / ตรวจนับ

- **รับเข้า +:** ผู้จัดการระบุจำนวน ต้นทุนต่อหน่วยของล็อต เลขอ้างอิงใบรับ/ล็อต และเหตุผล สร้างล็อตใหม่ รองรับต้นทุนต่างกัน เช่น 3 ชิ้น × 10 บาท และ 2 ชิ้น × 14 บาท
- **ปรับเพิ่ม + / ปรับลด −:** ผู้จัดการระบุจำนวนบวกตามปุ่ม และเหตุผล การลดจะถูกเก็บเป็นจำนวนติดลบ ห้ามลดจนยอดติดลบ
- **ตรวจนับ:** พนักงานหรือผู้จัดการระบุจำนวนที่นับจริงและเหตุผล สถานะ PENDING **ยังไม่เปลี่ยนสต๊อก** ผู้จัดการเลือกอนุมัติหรือปฏิเสธพร้อมเหตุผล
- หากมีการรับ/ขาย/ปรับ/คืนระหว่างรออนุมัติ จะบล็อกการอนุมัติ แม้ยอดรวมกลับมาเท่าเดิม ผู้จัดการต้องปฏิเสธและให้ตรวจนับใหม่ ไม่ทับยอดขายระหว่างทาง
- อนุมัติผลที่ต่างจากระบบจะสร้าง movement หนึ่งรายการ หากยอดตรงจะบันทึกการอนุมัติโดยไม่สร้าง movement จำนวน 0

ทุก movement มีจำนวนก่อน เปลี่ยน หลัง เหตุผล พนักงาน เวลา รหัสคำสั่ง และ reference ถ้ามี การรับเงินตัดสต๊อก/จำนวนล็อตในคำสั่งเดียวกัน การคืนสินค้าแบบรับกลับสต๊อกสร้าง movement และล็อตคืน ไม่เพิ่มกลับจากการคืนเงินอย่างเดียว

## ต้นทุนล็อตกับกำไร: นโยบายที่คงจากระบบเดิม

ระบบนี้ยังใช้ **ทุนมาตรฐานจากข้อมูลสินค้า ณ ตอนยืนยันขาย** เป็น snapshot ต้นทุนขายตามรุ่นเดิม การแก้ทุนหรือราคาขายไม่เปลี่ยนกำไรของธุรกรรมที่ขายแล้ว การเพิ่มสินค้าในบิล Station ล็อกราคาขายตอนเพิ่มรายการ แต่เก็บต้นทุนขายตอนรับเงิน หากราคาในตะกร้า POS เปลี่ยนก่อนชำระ ระบบเดิมจะให้เอาออกแล้วเพิ่มใหม่เพื่อยืนยันราคาใหม่

**ต้นทุนรับเข้าแต่ละล็อตแยกจากทุนมาตรฐาน** การรับล็อตแพงขึ้นไม่แก้ทุนขายให้อัตโนมัติ เจ้าของร้านเลือกแก้ทุนมาตรฐานผ่านหน้าสินค้าได้และมีประวัติต่างหาก ดังนั้น:

- มูลค่าตามล็อต = ผลรวมจำนวนเหลือในแต่ละล็อต × ต้นทุนรับเข้าล็อตนั้น
- มูลค่าตามทุนมาตรฐาน = คงเหลือ × ราคาทุนสินค้าในปัจจุบัน
- กำไรต่อ SKU = ยอดรับเงินจริงสุทธิของ SKU − ต้นทุนขาย snapshot หักกลับเมื่อคืนสินค้าเข้าสต๊อก
- การลดจำนวนล็อตใช้ล็อตเก่าก่อน **แต่ไม่ได้เปลี่ยนต้นทุนขายเป็น FIFO** และไม่ใช่ต้นทุนเฉลี่ยถ่วงน้ำหนัก
- สต๊อกยกมาจากระบบก่อนมีล็อตประเมินด้วยทุน catalog ณ ตอนเพิ่มโมดูล แสดงว่าเป็น **ยอดยกมาประมาณการ** และไม่เดาวัน/ราคาซื้อเก่า
- คืนสินค้าสร้างล็อตคืนด้วยทุนขาย snapshot เดิม ไม่ใช้ราคาทุนวันนี้ หากคืนเงินโดยไม่รับสินค้ากลับ จะไม่เพิ่มสต๊อกและไม่ย้อนต้นทุน

ตัวอย่าง SKU ใหม่สต๊อก 0 ทุนมาตรฐาน 12 บาท ราคาขาย 25 บาท รับ 3 ชิ้นทุนล็อต 10 และ 2 ชิ้นทุนล็อต 14 → มูลค่าตามล็อต **58 บาท** / มูลค่าทุนมาตรฐาน **60 บาท** ขาย 1 ชิ้น → เหลือ 4 ชิ้น มูลค่าตามล็อต **48 บาท** กำไรขาย **25 − 12 = 13 บาท** ทั้งสองค่าตอบคนละเรื่อง ไม่ควรตีความมูลค่าล็อตเป็นต้นทุนขาย FIFO

## รายงาน

ผู้จัดการใช้วัน/สัปดาห์/เดือน/ช่วงวันที่/ย้อนหลังทั้งหมดจากเมนูสรุปรายได้ เพื่อดูยอดขายและกำไรต่อ SKU จำนวนขาย/คืน และประวัติราคา/รับเข้า/ปรับ ตามผู้ทำรายการได้ สต๊อกและมูลค่าคงคลังแสดง **ยอดปัจจุบัน** ไม่ใช่ยอดคงเหลือย้อน ณ สิ้นวันที่เลือก

- ขายดี: เรียงจำนวนขายสุทธิจากมากไปน้อย แล้วรายได้สุทธิ
- ขายช้า: สินค้าเปิดขายเรียงจำนวนขายน้อยไปมาก รวมที่ยังไม่มีขายในช่วงนั้น เป็นการเปรียบเทียบปริมาณ ไม่ใช่การวัดอายุสินค้า
- สต๊อกต่ำ/หมด: ใช้ยอดปัจจุบันและขั้นต่ำของแต่ละ SKU
- ส่งออก CSV มีสต๊อก มูลค่า ยอดขาย/กำไร ประวัติ movement และประวัติทุน/ราคาขาย/รหัส พร้อมผู้ทำและเวลา Asia/Bangkok
- ประวัติล็อตและผลตรวจนับดูได้บนหน้าเว็บ ประวัติไม่ได้ลบเมื่อหมดล็อตหรืออนุมัติแล้ว

## สิทธิ์และข้อจำกัดก่อนใช้งานจริง

ผู้จัดการเพิ่ม/แก้ SKU รับเข้า ปรับสต๊อก อนุมัติตรวจนับ เปิดปิดขาย และดูต้นทุน/กำไร พนักงานค้นหา ใส่บิล ขายตาม POS และส่งตรวจนับได้ ฝั่งเซิร์ฟเวอร์ปฏิเสธคำสั่งรับเข้า/ปรับ/แก้ราคาเมื่อ actor เป็น staff และ `/api/inventory` เป็นรายงานผู้จัดการ กรองต้นทุนออกจาก staff state/API/สำรองข้อมูล รวมต้นทุนในล็อต

**ยังเป็น Demo identity ไม่ใช่ล็อกอินจริง:** ผู้ใช้เลือก manager เองได้ การกรองตามบทบาทจึงไม่ใช่การปกป้องความลับในระบบจริง ต้องเพิ่ม server-authenticated session และสิทธิ์จริงก่อนใช้ข้อมูลร้าน ไม่เปิดเซิร์ฟเวอร์นี้เป็นเว็บสาธารณะ Local Demo ไม่ป้องกันผู้ใช้เครื่องเปิด localStorage อ่านข้อมูล

Server Demo เก็บ SQLite ถาวรและใช้ BEGIN IMMEDIATE + revision + idempotency ครอบคลุมราคา สต๊อก ล็อต การขาย และอนุมัติ หลายเครื่องต้องใช้เซิร์ฟเวอร์เดียวกัน คำสั่งเก่าจากเครื่องอื่นจะถูกปฏิเสธให้ตรวจใหม่ ไม่รวมฐานหลายเครื่องที่รันแยกเซิร์ฟเวอร์

## วิธีทดสอบ

```powershell
npm test
npm run build:demo
```

Node tests ทดสอบเพิ่ม SKU/metadata ซ้ำ/รหัสเก่า เปลี่ยนราคาไม่แก้ประวัติ รับเข้าแยกทุนล็อต ยอดคงคลัง ตรวจนับและอนุมัติ สิทธิ์พนักงาน ป้องกันขายเกิน รับเงิน/คืนสินค้าไม่ซ้ำ และ SQLite หลังเปิดใหม่ พร้อมชุด Station/Timer/POS/รายได้/กำไร/ปิดกะเดิม

Browser tests (`npm run test:browser` เมื่อเตรียม Playwright/Chromium แล้ว) เปิดเว็บจริงทดสอบอัปโหลดรูป เพิ่ม SKU ตัวกรอง รับ 2 ล็อต ขาย POS พนักงานตรวจนับ ผู้จัดการอนุมัติ เปลี่ยนรหัส/ราคา ปรับเพิ่มลด CSV ปิดขาย รีเฟรช 12 Station ขนาด iPad/มือถือ และไฟล์ Local Demo ใช้ฐานในหน่วยความจำแยก ไม่แก้ฐานผู้ใช้
