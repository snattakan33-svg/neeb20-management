# คู่มือสรุปรายได้ / กระทบยอด / ปิดกะ — ข้อมูลทดสอบ

ระบบนี้ยังเป็น Demo ไม่เชื่อมธนาคาร บทบาทพนักงาน/ผู้จัดการเลือกได้เพื่อทดสอบ ไม่ใช่ authentication จริง ห้ามนำข้อมูลลูกค้าหรือรับเงินจริงมาใช้ ก่อน production ต้องทำ identity/สิทธิ์จริง, HTTPS, การตรวจบัญชีจริง, backup/restore และทดสอบอุปกรณ์

## เปิดฐานข้อมูลตัวอย่างบน Windows

1. ดาวน์โหลด ZIP รุ่นล่าสุด แตกไฟล์เป็นโฟลเดอร์ใหม่ ติดตั้ง Node.js 24 LTS
2. ดับเบิลคลิก **OPEN-RECONCILIATION-DEMO.cmd** เปิดหน้าต่าง server ค้างไว้ Browser จะเปิด `http://127.0.0.1:3001`
3. ตรวจป้ายข้อมูลทดสอบด้านบน แล้วกดเมนู **สรุปรายได้ / กระทบยอด / ปิดกะ**
4. เลือก **ย้อนหลังทั้งหมด** เพื่อเห็นกะก่อนหน้า เปลี่ยนกราฟแท่งเป็นวัน/สัปดาห์/เดือนได้ แท่งแสดงเฉพาะช่วงที่มีธุรกรรม ไม่มีการเดารายรับในวันว่าง เลือกพนักงานทุกคนก่อนตรวจยอดรวม

ตัวช่วยนี้ใช้ `.data/reconciliation-sample.sqlite` แยกจากฐานหลัก `.data/demo.sqlite` ถ้ามีฐานตัวอย่างแล้วจะใช้ต่อ ไม่สร้างทับ การรัน `npm run demo:reconciliation` ซ้ำจะปฏิเสธการเขียนทับ ชุดข้อมูลใน Git เป็น generator ไม่ใช่รายได้ของร้านจริง

ทางเลือก PowerShell:

```powershell
npm run demo:reconciliation
$env:NEEB20_DEMO_DB="$PWD\.data\reconciliation-sample.sqlite"
$env:PORT="3001"
npm start
```

หากสร้างไว้แล้ว ข้ามคำสั่งแรก ไม่ต้องลบไฟล์เก่าเพื่อให้สร้างใหม่ ส่วนระบบปกติเปิดด้วย START-NEEB20.cmd ที่พอร์ต 3000 และฐานหลักตามเดิม ระวังตัวแปร NEEB20_DEMO_DB/PORT ที่ตั้งใน Terminal จะคงอยู่ใน Terminal นั้น

## สูตรกระทบยอด (ภายในใช้จำนวนเต็มหน่วยสตางค์)

```text
เงินสดสุทธิจากรายการเงิน = รับเงินสด − คืนเงินสด
QR สุทธิตามระบบ          = รับ QR − คืน QR
เงินสดควรอยู่ในลิ้นชัก    = เงินทอนตั้งต้น + เงินสดสุทธิ + เติมสด − นำสดออก
ผลต่างสด                 = นับสดจริง − เงินสดควรอยู่ในลิ้นชัก
ผลต่าง QR                = QR สุทธิที่ตรวจจากบัญชี/หลักฐาน − QR สุทธิตามระบบ
ผลต่างรวม                = ผลต่างสด + ผลต่าง QR
เงินควรส่งมอบ            = เงินสดควรอยู่ในลิ้นชัก − เงินทอนที่เก็บไว้
ผลต่างส่งมอบเทียบยอดนับ  = ส่งสดจริง − (นับสดจริง − เงินทอนที่เก็บไว้)
ส่งจริงเทียบยอดคาด        = ส่งสดจริง − เงินควรส่งมอบ
```

เงินที่นำออกระหว่างกะอาจเป็นค่าใช้จ่าย/นำฝาก/ส่งเจ้าของ ต้องระบุเหตุผล รายงานแสดงแยก ไม่เดาว่าเงินนำออกทั้งหมดเป็นเงินส่งมอบเจ้าของ และไม่บันทึกเป็นยอดขาย/ลดรายรับ

สถานะยอดตรวจ **แยกจากสถานะกะ**:

- **ยอดตรง**: สด QR และส่งมอบไม่มีผลต่าง
- **เงินขาด / เงินเกิน**: ผลต่างที่มีเป็นทิศทางเดียวกัน
- **รอตรวจสอบ**: ยังไม่กรอกยอดจริง มีรายการไม่ทราบช่องทาง หรือผลต่างคนละทิศทาง เช่นสด −10 QR +10 แม้ผลต่างรวม 0 ก็ไม่ถือว่ายอดตรง

กะ APPROVED อาจยังมีผลต่างได้หากผู้จัดการอนุมัติรับทราบพร้อมเหตุผล ไม่ได้แปลว่าเงินครบ กรณีไม่ทราบช่องทางจากข้อมูลเก่า ระบบไม่อนุญาตให้อนุมัติด้วยการเดาว่าเป็น cash/QR ข้อมูลนั้นต้องแยกตรวจหลักฐานและยังเป็นรอตรวจสอบ รุ่นนี้ยังไม่มีเครื่องมือจัดประเภทช่องทางเก่าใหม่

## ลองส่งยอดและอนุมัติด้วยมือ

1. ในฐานตัวอย่าง กะที่ 3 มีเงินทอน 100 และยังเปิดอยู่ เลือกผู้ดำเนินการ **พนักงานทดสอบ 01**
2. เริ่ม Station 08 แล้วกดคิดเงิน รับสดทดสอบ 20 บาท บิลเป็น PAID เงินสดตามระบบในกะเพิ่ม 20 แต่การจบ/ย้ายไม่เพิ่มรายรับ
3. ในเมนูปิดกะ กด **เติมเงินเข้าลิ้นชัก** 10 บาท เหตุผล “ทดสอบเติมเงินทอน” แล้ว **นำเงินออก** 5 บาทพร้อมเหตุผล
4. กด **ส่งยอดปิดกะ** กรอก:
   - เงินสดนับจริง **125** บาท (100 + 20 + 10 − 5)
   - QR สุทธิที่ตรวจจริง **0** บาท
   - เงินทอนเก็บไว้ **100** บาท
   - เงินสดส่งมอบจริง **25** บาท
5. ส่งยอดแล้วจะเป็น SUBMITTED และไม่รับรายการเงินใหม่เข้ากะนี้ ปิด/แก้เงินเข้าออกไม่ได้ ถ้าจะขายต่อให้เปิดกะใหม่ก่อนรับ/คืนเงิน
6. เปลี่ยนผู้ดำเนินการเป็น **ผู้จัดการทดสอบ 01** เปิดรายละเอียดกะ แล้วกด **ตรวจสอบและอนุมัติปิดกะ** ระบุเหตุผลตรวจสอบ ข้อมูลเดิมถูกล็อกและมีชื่อ/เวลาอนุมัติ
7. ลองกลับเป็นพนักงาน จะไม่มีสิทธิ์แก้กะอนุมัติแล้ว ผู้จัดการสามารถกด **สร้างรายการแก้ไขหลังปิดกะ** เช่นนับ +1, ส่ง +1, QR 0 พร้อมเหตุผล จะเก็บ correction ใหม่และแสดงผลล่าสุดเงินเกิน 1 โดยยอดอนุมัติเดิม 125 บาทยังอยู่

ลองกรณียอดไม่ตรง: กรอกนับสด 120 แทน 125 ส่ง 20 จะขาด 5 บาท ต้องระบุเหตุผล หรือกรอกสด 115, QR 10 จะมีสดขาด/QR เกินที่หักกันแต่ยังรอตรวจสอบ ยกเลิกหน้าต่างก่อนส่งถ้าไม่ต้องการบันทึกตัวอย่างนี้

## QR: ยืนยันรับเงิน ไม่เท่ากับยืนยันเข้าบัญชี

Financial transaction QR ใหม่มีข้อมูลพนักงานยืนยันและเวลา พร้อม `qrBankStatus: UNVERIFIED` การส่งกะต้องระบุยอดสุทธิจากบัญชี/หลักฐานและอ้างอิงที่ตรวจ ผู้จัดการอนุมัติจะเก็บ `MANUALLY_REVIEWED` แยกในกะ **ไม่แก้ transaction ให้ดูเหมือนธนาคารยืนยันอัตโนมัติ** ห้ามใส่ password, OTP หรือข้อมูลลับในช่องหลักฐาน

Refund QR ในกะถัดมาอาจทำให้ยอด QR สุทธิตามระบบเป็นลบได้ ให้กรอกยอดสุทธิจากหลักฐานเป็นลบตามจริง Refund เงินสดต้องมีเงินในลิ้นชักตามระบบพอ หากไม่พอให้บันทึกเติมเงินพร้อมเหตุผลก่อน ไม่สร้างเงินสดเข้าลิ้นชักแบบเงียบ ๆ

## หลายกะ / เงินย้อนหลัง / รายงานพนักงาน

- ปัจจุบันเป็น **ลิ้นชักกลางหนึ่งชุด** จึงเปิดได้หนึ่งกะต่อเวลา แต่ส่งกะแล้วเปิดกะถัดไปวันเดียวกันได้โดยไม่ต้องรออนุมัติก่อน เหมาะหนึ่งเคาน์เตอร์ ไม่รองรับหลายลิ้นชักพร้อมกัน
- ผู้รับผิดชอบกะกับผู้ทำรายการเงินอาจเป็นคนละคน เช่นผู้จัดการคืนเงินในกะพนักงาน รายงานพนักงานจัดตามคนกดรับ/คืนเงิน ส่วนกระทบยอดจัดตามผู้รับผิดชอบลิ้นชัก ห้ามนำสองรายงานมาบวกซ้ำ
- ก่อนเปิดใช้กะครั้งแรก เงินจากโค้ดเดิมยังคงเก็บและแสดง “ยังไม่ผูกกะ” ไม่สร้างกะ/โยกเงินเก่าโดยเดา หลังเปิดกะครั้งแรกแล้ว ทุกคำสั่งรับ/คืนเงินใหม่ต้องมีกะ OPEN
- ผู้จัดการใช้ **สร้างกะย้อนหลัง** เลือกเวลาเริ่ม/สิ้นสุดแบบ Asia/Bangkok โดยช่วงเป็น `[เริ่ม, สิ้นสุด)` พร้อม float เงินเข้า/ออกรวมตามหลักฐาน ยอดจริง และเหตุผล ไม่อนุญาตช่วงซ้อน/รายการเงินเดียวอยู่สองกะ แล้วตรวจอนุมัติอีกขั้น
- Payment/refund ใหม่ผูกกะที่กำลังเปิดด้วย transaction IDs แบบ atomic จึงไม่มีช่องว่างจากการใช้เวลาสองเครื่องต่างกัน Refund ของบิลเก่าอยู่ในกะที่คืนเงิน ไม่แก้กะขายเดิม หากเหตุการณ์เวลาเดียวกันระดับ ms ใช้ assignment ที่บันทึกจริงตามลำดับคำสั่ง ไม่เดาจาก timestamp เพียงอย่างเดียว
- รายงานรายวัน/สัปดาห์ ISO/เดือน/ช่วง/ทั้งหมด ใช้ Asia/Bangkok วันสิ้นสุดรวมด้วย กะในรายงานเลือกกะที่เปิด/ส่ง/อนุมัติ/มี correction ในช่วงวันที่ ส่วนรายได้เลือกตามเวลารับ/คืนเงินจริง กะคร่อมเที่ยงคืนจึงอาจไม่เท่ากับรายงานรายวัน ห้ามบวกยอดกะกับยอดขายซ้ำ

## รายการต้องตรวจและส่งออก

เมนูมีบิลยกเลิก คืนเงิน ย้ายจุด แก้สินค้า ต่อเวลา บิลค้าง รายการช่องทาง/บิลไม่ครบ QR รอตรวจมือ เงินยังไม่ผูกกะ ผลต่างกะ และ correction พร้อมผู้ทำ/เวลาและรายละเอียด Audit

ส่งออก CSV ได้ทั้งสรุปรายได้/รายพนักงาน ธุรกรรม บิล และกะตามตัวกรอง หรือกด **พิมพ์รายงาน** Browser จะแสดง print dialog เลือกเครื่องพิมพ์หรือ Save as PDF ไม่ได้เชื่อมเครื่องพิมพ์ใบเสร็จ/ลิ้นชักเงินจริง CSV ใช้เวลา Asia/Bangkok (+07:00) มีป้ายข้อมูลทดสอบและป้องกันข้อความเป็นสูตร spreadsheet รายงานกะเก็บยอดเดิมตอนอนุมัติและรายการแก้ไขแยกจากยอดล่าสุด

## ความคงทนและสิทธิ์

ข้อมูลหลักและข้อมูลกะอยู่ SQLite ฝั่ง server บันทึกกะ/transaction assignments/การอนุมัติ/correction/Audit และ idempotency ใน transaction เดียวกัน ปิด server/refresh ไม่ทำให้ยอดหรือกะเริ่มใหม่ คำสั่งเดิมส่งซ้ำไม่บวกเงิน เติมเงิน ส่งยอด หรือ correction ซ้ำ

Submitted/Approved lock actual และรายการเงินเข้าออก Approved snapshot ไม่ถูกเขียนทับ correction มีผู้ทำ เวลา เหตุผล และ before/after Audit แต่ไม่มีการแก้ยอดขายจากการแก้นับเงิน

การตรวจบทบาทใน Demo ไม่แทนการพิสูจน์ตัวตนจริง และรายงาน/กราฟไม่แทนบัญชีภาษีหรือการตรวจธนาคาร ก่อนใช้จริงต้องทดสอบกระทบยอดเงินและสิทธิ์บนเครื่องจริง เพิ่มผู้ใช้จริง/approval, backup/restore ที่พิสูจน์ได้, HTTPS, schema และการคุ้มครองข้อมูล
